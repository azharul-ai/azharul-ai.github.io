Monolith, modular monolith, or microservices?

Architecture is not a maturity contest. Choose the simplest option that fits the business boundaries, team structure, scale, and ability to operate it.

By Md. Azharul Islam September 9, 2026 7 min read

Requirements and scale

Architecture discussions often treat monoliths and microservices as opposing levels of maturity. That framing is misleading. Each option creates different boundaries and operational responsibilities. A small team can build a poor monolith or an unnecessarily complicated collection of services. The architecture label does not guarantee the design quality.

The practical question is: which architecture fits the current business boundaries, team structure, scale, and ability to operate distributed systems?

Architecture and ownership

A monolith packages the application as one deployable unit. Its modules can still be well designed, but deployment and runtime scaling happen together.

A modular monolith remains one deployable application while enforcing internal boundaries. Modules own responsibilities and expose deliberate interfaces instead of sharing everything. This can provide many design benefits associated with services without introducing network communication and distributed deployment.

Microservices split the system into independently deployable services. Each service should own a meaningful business capability and its data. This supports independent scaling and delivery, but introduces network failure, eventual consistency, observability, versioned contracts, and more infrastructure.

The decision is therefore about boundaries and operations rather than repository count.

Four dimensions make the trade-off clearer. A deployment boundary decides what must be released together. A data boundary decides who can change each record. A failure boundary decides whether one unhealthy capability can consume resources needed by others. An ownership boundary decides which team can make changes without coordinating every detail.

A monolith combines the deployment boundary but can still enforce data and ownership boundaries in code. Microservices create stronger runtime boundaries only when contracts and data ownership are genuinely independent. Splitting processes without splitting responsibility adds distance rather than autonomy.

The modular monolith occupies an important middle ground. It keeps one deployment while making responsibilities and contracts visible. If later evidence supports extracting a capability, an existing module boundary provides a safer starting point.

Request and data flow

Consider an early commerce product with catalogue, ordering, payment, and notification features. One small team owns the whole product and releases it together. Traffic is moderate, and there is no demonstrated need to scale payment separately.

A modular monolith can give each capability a clear module inside one application. The ordering module cannot update catalogue tables directly. Payment is accessed through a defined application interface. One database may be used initially, but table ownership and transactions remain explicit.

Later, the payment capability may need stronger isolation, a separate compliance boundary, and an independent release cycle. That evidence can justify extracting it as a service. The existing module boundary makes extraction safer because callers already use a deliberate contract.

Starting with four services on day one would add deployment pipelines, credentials, network calls, and cross-service failure before those costs solve a measured problem.

Now imagine the product grows to several teams. Catalogue releases frequently while payment changes slowly under stricter review. Payment traffic follows a different pattern, and failures must not consume ordering resources. Those are concrete extraction signals.

Extraction is still not free. The order workflow can no longer rely on one local transaction across payment and inventory. It needs durable state, idempotent messages, and a way to reconcile uncertain outcomes. The HLD should show how those responsibilities change instead of presenting extraction as moving code into another folder.

The reverse decision is valid too. If several tiny services always deploy together, share one database, and require coordinated changes, combining them into a modular application can reduce operational cost without losing meaningful business boundaries.

Trade-offs and alternatives

  • Choosing microservices because large companies use them without sharing their scale or organization.
  • Calling an application modular while every module reads and changes the same data directly.
  • Creating services around technical layers such as controllers or repositories instead of business capabilities.
  • Sharing one database schema between services and assuming they are independent.
  • Ignoring the cost of tracing, retries, timeouts, deployments, and on-call support.
  • Keeping a monolith with no internal boundaries until every change affects unrelated features.
  • Extracting a service before its ownership and contract are understood.
A costly result: A distributed monolith has separate deployments and network calls with the tight coupling of one application.

Operational readiness checklist

  1. How many teams need to deploy independently?
  2. Which business capabilities have stable ownership boundaries?
  3. Is independent scaling based on measurements or expectation?
  4. Can the team operate logs, metrics, traces, alerts, and deployments for many services?
  5. Which transactions currently require strong consistency?
  6. Can module boundaries be enforced inside one application first?
  7. What specific problem would a service extraction solve now?
  8. How will contracts and data ownership be governed?

Choose the simplest option that satisfies known requirements while preserving useful boundaries. Revisit the decision when scale, ownership, regulation, or delivery patterns provide new evidence.

Design recommendation

  • A modular monolith is often a strong default for one team and an evolving domain.
  • Microservices buy independent deployment and scaling by accepting distributed-system costs.
  • Architecture should evolve from evidence and clear boundaries rather than fashion.
